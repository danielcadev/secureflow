# SecureFlow v1.0.0-rc.1

<!-- secureflow-release-state: final -->

This release candidate introduces the SecureFlow v1 Security Case as an additive local evidence and decision boundary. It is a prerelease for evaluation and release qualification, not a stable or production-readiness claim.

## Highlights

- `secureflow-security-case-v1` binds an explicitly authorized local target and optional revision to source provenance, evidence hashes, typed candidates, staged recommendations, and named human decisions.
- Core semantic validation rejects malformed identifiers, hashes, timestamps, references, duplicates, duplicate candidate decisions, and unauthorized source-to-candidate mappings; the standalone JSON Schema validates structural interoperability only.
- Secure Engine may originate only engine candidates, validated Secure Skill imports remain contextual candidates, and SARIF 2.1.0 imports remain external-tool candidates. Agent sources cannot originate v1 candidates.
- The local stdio MCP bridge exposes only case reading, candidate investigation, and recommendation staging. It has no tool or dispatch route for a final decision and no provider transport.
- Review Room loads bounded local case bytes with strict UTF-8 decoding, applies the same semantic authority boundary before rendering, marks artifact-derived WebMCP content as untrusted, and retains its browser audit as a local draft rather than a Core decision.
- The cumulative candidate retains the offline trusted-catalog lifecycle, CodeSupply demonstration, pinned release controls, deterministic source archive, host-specific Linux bundle, SBOM, provenance, and adjacent checksums from the current development line.

## Verification and artifacts

The local release lane uses pinned Rust 1.92.0 to run release-control tests, formatting, workspace Clippy with warnings denied, workspace tests, a release build, locked dependency fetching, trusted-catalog evidence, SBOM generation, and deterministic packaging from the exact committed tree. The resulting source archive and host-specific Linux bundle each receive an adjacent SHA-256 checksum.

Hosted CI, tag-triggered attestations, and publication are separate future actions bound to the exact candidate commit. This note does not claim those actions have occurred.

## Limits and authority

SecureFlow remains local-first and requires explicit authorization for target analysis. Only a named human reviewer may record a final `validated`, `rejected`, or `abstained` decision; scanner results, imports, browser audit entries, and agent recommendations remain non-authoritative candidates or drafts.

This candidate provides no target-network transport, remote reconnaissance, exploitation, provider transmission, autonomous patching, complete-security guarantee, production-safety claim, or demonstrated superiority over human researchers. Structural schema conformance alone is not semantic acceptance; use `secureflow case-validate` or Review Room's semantic validator.

Source archive byte equality is checked for the compared local builds. The Linux bundle is host-specific and does not claim cross-host binary reproducibility. Checksums and any later workflow attestations establish artifact integrity and provenance, not that the code, dependencies, imported evidence, or analyzed targets are vulnerability-free. The release tag may be unsigned if one is later created.
