# SecureFlow v1.0.0-rc.3

<!-- secureflow-release-state: final -->

This release candidate hardens the Secure Engine failure boundary discovered by the first repository-to-Security-Case use of the universal Codex integration. It is a prerelease for local workflow evaluation, not a stable or production-readiness claim. The immutable `v1.0.0-rc.2` tag remains unchanged.

## Highlights

- Engine process failures retain a bounded, terminal-safe stderr diagnostic and state that no evidence was accepted. Resource failures direct the operator to narrow the authorized target instead of disabling the sandbox.
- Reports that explicitly declare truncated analysis fail closed and cannot become successful zero-candidate runs or Security Cases.
- The bundled skill creates a case only from a completed SecureFlow run manifest. It forbids automatic sandbox downgrade, direct-report substitution, synthesized candidates, and repository-wide claims from component cases.

## Verification and limits

The regression reproduces Secure Engine RC2 aborting with status 134 on an authorized Mitiquete monorepository snapshot. The corrected adapter retains the bounded allocation failure diagnostic, writes no report or manifest, and accepts a smaller authorized component through sandboxed scan, case creation, and semantic case validation.

This candidate does not make the legacy Engine's full report fit every monorepository. It makes that resource limit explicit and non-ambiguous while preserving the option to use separate authorized component cases. Component success is not repository-wide coverage, and no scanner output or agent recommendation is a human vulnerability decision.
